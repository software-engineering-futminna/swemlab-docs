Assigned automatically to the departmental GitHub account (software-engineering-futminna) or any GitHub account with a verified softwareng@futminna.edu.ng address.

  • Views and manages all courses across all lecturers in the department
  • Full access to all course leaderboards and Senate CSV grade exports

Assigned automatically to any lecturer or staff member who has a verified @futminna.edu.ng email (excluding @st.futminna.edu.ng) attached to their GitHub account. Staff may keep their personal email as primary on GitHub—SWE-MLAB detects verified secondary university emails automatically.

Assigned automatically to students with a verified @st.futminna.edu.ng email on GitHub. Accounts without a verified FUTMinna email are declined with /?error=institutional_email_required.

SQL & Git Maintenance Runbook

Standard SQL queries and Git commands for routine departmental maintenance and edge-case recovery.

1. Departmental Super Admin Database Sync

Ensures softwareng@futminna.edu.ng and GitHub account software-engineering-futminna hold super_admin privileges: 

UPDATE users
SET role = 'super_admin',
    institutional_verified = true
WHERE LOWER(email) = 'softwareng@futminna.edu.ng'
   OR LOWER(username) = 'software-engineering-futminna';

2. Update Staff Who Logged In Before Email Verification

If a lecturer signed in before verifying their @futminna.edu.ng email on GitHub, run this query once: 

UPDATE users
SET role = 'instructor',
    institutional_verified = true
WHERE LOWER(email) LIKE '%@futminna.edu.ng'
  AND LOWER(email) NOT LIKE '%@st.futminna.edu.ng'
  AND role != 'super_admin';

3. Reset Stale Repository Migration URL

If a team repository URL points to a deleted placeholder in the organization, reset it to the student's personal repo before clicking Migrate to Org: 

UPDATE teams
SET repo_url = 'https://github.com/StudentOwner/repo-name',
    repo_full_name = 'StudentOwner/repo-name'
WHERE id = <team_id>;

4. Sync Personal Repository into Empty Org Repo

If a team pushed their commits to a personal repo while their organization repo remained empty: 

git clone https://github.com/StudentUsername/PERSONAL-REPO.git temp_sync
cd temp_sync
git remote set-url origin https://github.com/software-engineering-futminna/ORG-REPO.git
git push origin main --force
cd .. && rm -rf temp_sync

01. Pedagogical Framework & Academic Curriculum

Course: FUTM-SWE-221: Individual Software Development Project I • Semester: Second Semester • Department: Department of Software Engineering, FUTMinna

View Markdown Source

1. Pedagogical Vision

SWE-MLAB was engineered to bridge academic classroom theory and commercial software engineering practice. Rather than submitting static code zip files, students develop and deploy cloud-native applications across structured agile sprints.

2. 4-Sprint Lifecycle

Sprint Timeline Objectives & Learning Outcomes
Sprint 1 Weeks 1–3 Architecture & Wireframing: Problem formulation, public REST API evaluation, component tree planning, and role allocation.
Sprint 2 Weeks 4–7 Async API Integration: Asynchronous JavaScript (fetch, async/await), JSON schema validation, error boundaries, and rate limit resilience.
Sprint 3 Weeks 8–10 Client-Side Resilience & UX: Offline storage (localStorage/Service Workers), PWA manifests, Swiss typography, and accessibility contrast.
Sprint 4 Weeks 11–13 Cloud Deployment & Defense: Continuous delivery on Netlify/Vercel/Railway, semantic commit review, and oral defense.

3. Evaluation Rubrics

Submissions are scored on a standardized 100-point rubric:

  • Core Functionality & Business Logic (40%): Feature completeness, dynamic state management, filtering, and responsive interactivity.
  • API Integration & Resilience (20%): Robust asynchronous fetching, error fallback states, and defensive JSON schema parsing.
  • UI/UX & Swiss Design Standards (20%): Strict grid alignment, typographic contrast, mobile touch responsiveness, and zero visual clutter.
  • Git Hygiene & Collaboration (20%): Commit distribution among team members, meaningful pull requests, and repository README documentation.

4. Student Developmental Context

These submissions represent foundational 200-level undergraduate coursework. They demonstrate practical mastery of core web and API principles rather than hardened commercial platforms.

docs/03-github-org-migration-pipeline.md

03. GitHub Organization Migration Pipeline

View Markdown Source

1. The Migration Problem

Students often begin team projects in personal GitHub repositories (Taiwrash/project-name or Student/repo). Manually copying code via file uploads destroys commit histories, pull request discussions, and author attribution.

2. The SWE-MLAB Automated Transfer Pipeline

SWE-MLAB implements an automated 1-click migration pipeline leveraging GitHub's Repository Transfer API:

[Instructor Dashboard]
        │  Click "Migrate to Org"
        ▼
[SWE-MLAB Backend (/api/v1/teams/:id/migrate-repo)]
        │
        ├── 1. Load team members & GitHub usernames from DB
        ├── 2. Clean up any stale placeholder repository in the organization
        ├── 3. Execute GitHub Transfer API: POST /repos/{source_owner}/{source_repo}/transfer
        │      └── Handle HTTP 202 Accepted via go-github (*github.AcceptedError)
        ├── 4. Set repository visibility to Public: PATCH /repos/software-engineering-futminna/{repo}
        ├── 5. Add all team members as collaborators: PUT /repos/{org}/{repo}/collaborators/{username}
        └── 6. Save updated organization repo URL in PostgreSQL

3. Asynchronous 202 Handling

When GitHub schedules repository transfers, it returns HTTP 202 Accepted. SWE-MLAB intercepts *github.AcceptedError, extracts the destination URL, and updates the database without treating the asynchronous scheduling as a failure.

04. REST API Specification

View Markdown Source

1. Authentication Endpoints

  • GET /auth/github: Initiates GitHub OAuth authentication.
  • GET /auth/github/callback: Exchanges OAuth authorization code for session token and verifies student profile.
  • GET /api/v1/user/profile: Retrieves authenticated user data and enrolled courses.
  • POST /auth/logout: Invalidates active session token.

2. Course & Activity Endpoints

  • GET /api/v1/courses: Lists all available courses.
  • POST /api/v1/courses: Creates a new course (Instructor/Admin only).
  • GET /api/v1/courses/:id: Retrieves course details, syllabus, and enrolled students.
  • POST /api/v1/courses/:id/enroll: Enrolls student into course.
  • GET /api/v1/courses/:id/activities: Lists activities and milestones for a course.

3. Team & Repository Migration Endpoints

  • POST /api/v1/projects/:id/teams: Creates a new project team.
  • POST /api/v1/teams/:id/invitations: Invites a student into a team.
  • POST /api/v1/invitations/:id/accept: Accepts pending team invitation.
  • POST /api/v1/teams/:id/migrate-repo: Transfers team repo into the institutional organization (Instructor only).

4. Submissions & Grading

  • POST /api/v1/activities/:id/submit: Submits repository and live deployment URLs.
  • POST /api/v1/webhooks/github: Ingests GitHub push/PR events for telemetry.
  • POST /api/v1/submissions/:id/grade: Submits rubric score and markdown feedback.

docs/08-troubleshooting-runbook.md

08. Operational Troubleshooting & Runbook

View Markdown Source

1. Rate Limit Handling (403 Forbidden)

  • Problem: GitHub API calls fail with rate limit exceeded (60/hr).
  • Solution: Pass the user's active SessionToken via oauth2.StaticTokenSource, which expands rate limits to 5,000 req/hr.

2. Stale Migration Recovery

  • Problem: "The recorded repo URL points to the org but the repo no longer exists."
  • Solution: Reset the team's repo_url in the database to point to the actual source repo (Taiwrash/repo or Student/repo), then re-run migration.

3. Syncing Empty Org Repositories

Problem: An organization repository was initialized empty while student code exists in a personal repository.

git clone https://github.com/StudentLead/PERSONAL-REPO.git /tmp/sync_repo
cd /tmp/sync_repo
git remote set-url origin https://github.com/software-engineering-futminna/ORG-REPO.git
git push origin main --force
rm -rf /tmp/sync_repo

 Automated Pedagogical Cloud for Software Engineering Education

1. Executive Summary & Institutional Context

1.1 The Challenge in Modern Software Engineering Pedagogy

Undergraduate software engineering education at scale faces significant systemic bottlenecks:

  • Dispersed Code Repositories: Students frequently host coursework on disparate personal accounts, making code audit, plagiarism detection, and institutional archival difficult.
  • Asymmetric Team Contributions: Assessing individual participation within collaborative student teams is often opaque without commit telemetry and automated tracking.
  • Delayed Feedback Loops: Manual evaluation of projects by instructors causes evaluation lag, denying students rapid formative feedback during sprint cycles.
  • Friction in Cloud Deployment: Moving student code from local development environments to live web deployments involves non-trivial configuration hurdles.
1.2 The SWE-MLAB Solution

SWE-MLAB (Software Engineering Machine Laboratory) is an integrated pedagogical cloud platform engineered specifically for the Department of Software Engineering at FUTMinna. SWE-MLAB bridges the gap between academic theory and industry practices by providing:

  • 1Automated GitHub Organization Management: All student coursework, labs, and group projects are automatically created, permissioned, or transferred into the institutional GitHub organization (software-engineering-futminna).
  • 2Institutional Verification: Restricts enrollment to authorized institutional email domains (@st.futminna.edu.ng for students; @futminna.edu.ng for instructors).
  • 3Continuous Activity Tracking: Ingests Git commits, pull requests, and co-author tags to provide real-time contribution analytics.
  • 4Instantaneous Repository Migration: Allows instructors to transfer student repositories into the central organization in milliseconds while preserving full Git history.
  • 5Interactive Academic Showcase: Automatically indexes student deliverables, public live URLs, and team dossiers into a responsive, accessible public showcase.

2. Pedagogical Framework & Academic Curriculum

2.1 Course Alignment: FUTM-SWE-221

SWE-MLAB was piloted during the 2025/2026 academic session for FUTM-SWE-221: Individual Software Development Project I (Second Semester). The course is structured around real-world software engineering learning milestones:

  • Sprint 1 — Proposal & Architectural Wireframing: System design, REST API selection, and component breakdown.
  • Sprint 2 — Asynchronous Data Integration: Asynchronous JavaScript (fetch, async/await), schema validation, and handling rate limits / network dropouts.
  • Sprint 3 — Client-Side Resilience & Offline-First UX: Progressive Web App (PWA) asset caching, localStorage / IndexedDB persistence, and Swiss design principles.
  • Sprint 4 — Production Cloud Deployment & Oral Defense: Automated staging on Netlify/Vercel/Railway, continuous integration, and technical defense.
2.2 Academic Scope & Student Developmental Expectations

  • Developmental Context: Projects represent foundational milestones for 200-level undergraduates; they are academic demonstrations rather than hardened enterprise platforms.

3. System Architecture & Technology Stack

SWE-MLAB is built on a high-performance, containerized micro-monolith architecture designed for high availability, low latency, and zero build friction.

3.1 Backend Specifications

  • Language: Go (Golang) 1.22+
  • HTTP Routing: Gin Framework (github.com/gin-gonic/gin)
  • ORM & Database Client: GORM (gorm.io/gorm) with postgres driver (gorm.io/driver/postgres)
  • Third-Party API Client: go-github (github.com/google/go-github/v60/github)
  • Authentication: OAuth2 (golang.org/x/oauth2) with GitHub Provider
  • Monitoring & Crash Reporting: Sentry Go SDK (github.com/getsentry/sentry-go)

3.2 Frontend Specifications

  • Core Library: React 18
  • Bundler & Tooling: Vite 5
  • Routing: React Router v6
  • UI Architecture: Custom Swiss International Typographic Design System (pure Vanilla CSS with CSS custom properties, zero Tailwind dependency)
  • Typography: Inter (General Text), JetBrains Mono (Code & Telemetry)

3.3 Infrastructure & Cloud Persistence

  • Production Database: Neon Serverless PostgreSQL with connection pooling (ep-falling-darkness-al1utzuu-pooler.c-3.eu-central-1.aws.neon.tech)
  • Containerization: Multi-stage Docker containers with Alpine Linux base
  • Reverse Proxy: Nginx with gzip compression, security headers, and Single Page Application fallback routing

4.4 GitHub Organization Provisioning & Migration Pipeline (TransferToOrg)

Students often start projects in personal GitHub repositories (Taiwrash/project-name or MoTaC1/LIVE-WEATHER-APP). Manually copying code via file uploads loses commit history and author attribution. SWE-MLAB solves this via GitHub's Repository Transfer API:

  • 1. Single API Transfer: Executes client.Repositories.Transfer(ctx, owner, repo, TransferRequest{NewOwner: org}).
  • 2. Asynchronous 202 Handling: GitHub returns HTTP 202 Accepted when scheduling large repository transfers. The SWE-MLAB backend captures *github.AcceptedError and resolves the target URL immediately without failing.
  • 3. Stale Repository Cleanup: If an empty placeholder repo exists in the org from a previous attempt, SWE-MLAB detects and deletes it prior to initiating the transfer.
  • 4. Visibility & Permissions Enforcement: Automatically updates repository visibility to Public and re-invites all registered team members as repository collaborators.

9. Operational Troubleshooting & Failure Recovery

  • 9.1 Handling GitHub API Rate Limits (403 Forbidden): Anonymous calls hit 60/hr. All methods in github_service.go pass the active SessionToken via oauth2.StaticTokenSource to guarantee 5,000 requests/hour.
  • 9.2 Resolving Stale Migration Records: If a previous migration recorded an org URL that was later deleted on GitHub, update teams.repo_url and teams.repo_full_name in PostgreSQL to the student's personal repo and click Migrate to Org again.
  • 9.3 Syncing Unmigrated Student Codebases: If an org repository has 0 commits because the student pushed to a personal repo, clone the personal repo, set origin to https://github.com/software-engineering-futminna/ORG-REPO-NAME.git, and run git push origin main --force.

  • 3.2.2 Creating Weekly Lab Activities (Tab 2: Weekly Activities):
    • Method A — AI Activity Generator (POST /api/v1/courses/:id/activities/generate): Click AI Generate, enter Topic, Learning Objectives, Language (go, python, javascript, java, rust), and optional Lecture Excerpt; Gemini AI generates title, description, Markdown instructions, step-by-step tasks, dependencies, test_command, max_score, and industry_skills.

Module 03: Lecture Notes RAG Pipeline & Student AI Tutor (60 Mins)
  • 1. Strict File Validation (UploadLectureNote): Instructors upload a .pdf or .docx file (up to 20 MB); backend verifies file extension and binary magic bytes (%PDF for PDFs; PK\x03\x04 ZIP header for DOCX).
  • 2. Asynchronous Background Indexing (go h.rag.ProcessLectureNote): Sets status to Processing, extracts text in a background goroutine, splits into semantic LectureChunk records in PostgreSQL, and transitions status to Ready.
  • 3. Live RAG Telemetry Bar: Displays Notes Uploaded (total_notes), Ready for AI (ready_notes), Knowledge Chunks (total_chunks), and Student Chat (enabled when ready_notes > 0).
  • 4. Student AI Chat Experience (AIChatWidget.jsx): Enrolled students open the AI Chat widget on /dashboard and ask questions (up to 2,000 characters) answered from retrieved LectureChunk passages.
Module 04: Teams, Projects, Repo Launch & 1-Click Org Migration Pipeline (60 Mins)

1. Executive Summary

SWE-MLAB (Software Engineering Machine Laboratory) is an integrated pedagogical cloud platform engineered for the Department of Software Engineering at the Federal University of Technology Minna (FUTMinna). The platform automates the software engineering educational lifecycle by providing:

  • 1Automated GitHub Organization Management: All coursework and student teams are provisioned and governed under the institutional organization (software-engineering-futminna).
  • 2Institutional Identity Enforcement: Verification of student emails under the @st.futminna.edu.ng domain (and staff instructors under @futminna.edu.ng).
  • 3Continuous Telemetry & Activity Tracking: Tracking individual commit contributions, branch hygiene, and milestone progress.
  • 4Instantaneous Repository Migration (TransferToOrg): Transferring personal repositories into the institutional organization in milliseconds with preserved commit histories.
  • 5Interactive Public Showcase: Live exhibition of student project deliverables, API integrations, and team rosters.

3. Role-Based User Manuals & 4. Repository Migration Pipeline

  • Students (@st.futminna.edu.ng): Sign in with GitHub, verify institutional email, join course FUTM-SWE-221, create/join project teams, push code, deploy to cloud staging, and submit project URLs.
  • Instructors (@futminna.edu.ng): Provision courses, define project rubrics, monitor real-time student team telemetry, execute 1-click repository migrations into software-engineering-futminna, grade submissions with markdown feedback, and update public showcases.
  • Super Administrators (softwareng@futminna.edu.ng): Manage GitHub Organization OAuth applications, configure Neon Serverless PostgreSQL connection pooling, monitor Sentry error traces, and execute disaster recovery runbooks.
